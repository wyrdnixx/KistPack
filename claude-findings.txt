  BUG 1 — Falsche DataTable beim CSV-Re-Export (Form1.cs:918)

  // btnRegenCSV_Click, wenn cb_SubmitCsv.Checked == true:
  if (!CSVExport(dt, csvPath + selectedChargeNumber + ".csv"))
  //              ^^  FALSCH: exportiert die aktuelle (evtl. leere) Arbeits-DataTable

  tmpDT wird in Zeile 909 aus der DB geladen, aber dann ignoriert. Stattdessen wird dt (Tab "Kiste packen") exportiert, das nach createNewCharge() leer sein kann. Die CSV-Datei auf dem
  Netzwerkpfad wird mit leeren Daten überschrieben.

  BUG 2 — VORNAME und NAME vertauscht (ArchDB.cs:38-39)

  Die SQL-Abfrage liefert die Spalten in dieser Reihenfolge:
  SELECT FALLID, PATID, GEBDAT, VORNAME, NAME, F_STORNO
  --                     Index:   3        4

  Aber der Code liest:
  string nachname = dr.GetString(3); // liest VORNAME → falsche Variable
  string vorname  = dr.GetString(4); // liest NAME    → falsche Variable

  Das Ergebnis: pv.Vorname enthält den Familiennamen (NAME), pv.Nachname enthält den Vornamen (VORNAME). Alle Anzeigen in der Tabelle und alle CSV-Exporte sind damit dauerhaft falsch
  beschriftet.

  ---
  BUG 3 — Doppelter INSERT in Testmethode (KistPackDB.cs:285-286)

  cmd.ExecuteNonQuery();
  cmd.ExecuteNonQuery(); // ← zweimal!
  transaction.Commit();

  testInsertDbTransaction führt den INSERT-Befehl zweimal aus, was zu einem Doppeleintrag führt. Scheint toter Testcode zu sein, der nicht entfernt wurde.

  LOGIC 1 — Button "PDF erneut drucken" tut nichts (Form1.cs:295)

  Der gesamte Handler ist in if (!chargeWasSavedToDB) eingeschlossen:

  private void btnFinishCharge_Click(object sender, EventArgs e)
  {
      if (!chargeWasSavedToDB)  // wenn true → der ganze Block wird übersprungen
      {
          // ...
          btnFinishCharge.Text = "PDF erneut drucken"; // Button umbenannt...
          // ...
      }
      // ...aber kein Code für den Fall chargeWasSavedToDB == true
  }

  Nachdem die Charge gespeichert wurde, heißt der Button "PDF erneut drucken", aber ein Klick darauf löst gar nichts aus. Der Nutzer denkt, der Druck wird wiederholt, es passiert aber
  nichts. PDF-Regeneration muss dann umständlich über den Such-Tab erfolgen.

  LOGIC 2 — Falsche Fehlermeldung bei DB-Verbindungsausfall (Form1.cs:46-54)

  string dbversion = kistPackDB.getKistPackDBVersion(); // DB down → zeigt "Verbindungsfehler" → gibt null zurück
  if (dbversion != assemblyVersion)                     // null != "1.0.5.0" → true
  {
      MessageBox.Show("Programmversion ... stimmt nicht mit Datenbank Version überein."); // FALSCHE Meldung!

  Bei einem DB-Ausfall sieht der Nutzer zunächst "Verbindungsfehler" und dann sofort "Versions-Mismatch". Die zweite Meldung ist irreführend und falsch.

  ---
  LOGIC 3 — Charge-Nummern-Kollision bei gleichem Mandant/Minute (Form1.cs:173)

  tbCharge.Text = cbMandant.Text + DateTime.Now.ToString("yyyyMMddHHmm");

  Das Format geht nur bis auf Minuten genau. Werden zwei Charges vom gleichen Mandanten innerhalb derselben Minute angelegt (z.B. nach schnellem Abschluss), entstehen identische
  Charge-Nummern. Das kann Datenbankprobleme und fehlerhafte Suche verursachen.

  ---
  LOGIC 4 — Teilfehler hinterlässt inkonsistenten UI-Zustand (Form1.cs:298-342)

  Wenn saveDtToDB erfolgreich ist, CSV-Export aber fehlschlägt:
  - Daten sind in der DB gespeichert
  - chargeWasSavedToDB = true
  - Button zeigt "PDF erneut drucken"
  - Aber wegen LOGIC 1 tut der Button nichts mehr
  - createNewCharge() wird nicht aufgerufen, die alte Charge bleibt in der Tabelle sichtbar

  Der Nutzer kann jetzt weder eine neue Charge anlegen noch das PDF erzeugen, ohne die App neu zu starten oder den Such-Tab zu nutzen.

  PROGRAMMIERFEHLER

  ---
  PROG 1 — StreamWriter ohne using-Block (Form1.cs:783)

  StreamWriter sw = new StreamWriter(strFilePath, false);
  // ... verarbeitung ...
  sw.Close(); // ← wird nicht erreicht wenn Exception auftritt

  Tritt eine Exception auf, bleibt das Dateihandle offen. Ein zweiter Export-Versuch würde dann mit "Datei wird verwendet" scheitern. Lösung: using (StreamWriter sw = ...).

  ---
  PROG 2 — Kein Rollback im Fehlerfall (KistPackDB.cs:246-250)

  catch (Exception ex)
  {
      MessageBox.Show(...);
      // ← kein transaction.Rollback()!
  }
  // using-Block disposed die Connection → implizierter Rollback durch den DB-Server

  Kein explizites transaction.Rollback() im catch-Block. Funktioniert zwar durch impliziten Rollback beim Dispose, ist aber fehlerhafte Praxis und unklar.

  ---
  PROG 3 — SELECT * mit Spalten-Index-Zugriff (KistPackDB.cs:103-115)

  string query = @"SELECT TOP (50) * FROM Chargen WHERE Fallnummer = @Fallnummer";
  // Liest dann: dr.GetString(1) bis dr.GetString(12) - Index 0 wird übersprungen (ID?)

  Bei jeder Schemaänderung (neue Spalte, Umbenennung, Umsortierung) verschiebt sich die Zuordnung. Das führt zu stillen Datenverfälschungen. Spalten sollten explizit benannt werden.

  ---
  PROG 4 — SqlCommand nicht disposed (mehrere Stellen in KistPackDB.cs)

  SqlCommand implementiert IDisposable. In getKistPackDBVersion, getKistPackDBMerkmale, getKistPackDBExternalArchiveCall und searchWildcard wird SqlCommand ohne using-Block verwendet,
  was zu Ressourcenlecks führt.

  ---
  PROG 5 — MessageBox.Show im Thread-Pool-Thread (ArchDB.cs:49)

  // GetVisitFromArchive wird aufgerufen via:
  Task<PatientVisit> myTask = Task.Run(() => GetVisitFromArchive(_Fall));
  // ...und in GetVisitFromArchive:
  catch (Exception ex)
  {
      MessageBox.Show(...); // UI-Aufruf auf einem Background-Thread!
  }

  MessageBox.Show aus einem Task.Run-Callback ist technisch unsicher in WinForms (kein STA-Thread). Kann in seltenen Fällen zu Deadlocks oder fehlerhafter Anzeige führen.

  ---
  PROG 6 — testInsertDb und testInsertDbTransaction fehlt Merkmal-Spalte

  Beide Testmethoden enthalten keinen @Merkmal-Parameter, obwohl die Chargen-Tabelle diese Spalte in v1.0.5 bekommen hat. Falls die Spalte NOT NULL ist, würden diese Methoden bei Aufruf
   scheitern. Die Methoden scheinen toter Testcode zu sein, sollten aber entweder entfernt oder angepasst werden.
